# @RunPeriodically

`@RunPeriodically` runs a `Node` method on a fixed-rate loop. Use it for continuous work: driving, PID control, publishing state.

```java
@RunPeriodically(hz = 50)
public void update() { /* math, state machines — no hardware */ }

@RunPeriodically(hz = 50, hardware = true)
public void drive() { /* touches motors — runs on the hardware thread */ }
```

## Attributes

| Attribute | Type | Default | Meaning |
| --- | --- | --- | --- |
| `hz` | `int` | `20` | target frequency in hertz. Must be `> 0`; an invalid value logs a warning and skips the loop. |
| `hardware` | `boolean` | `false` | when `true`, the loop runs on the single dedicated hardware thread instead of the scheduler pool. |
| `labels` | `String[]` | `{}` | gate labels for hardware ticks — only meaningful with `hardware = true`. |

## Method signature rules

- **No parameters.** Pull inputs with `getLatestValue` inside the body.
- **Not static.** The binder invokes it reflectively on the node instance.
- The annotation is **repeatable** — one method may run at multiple rates (rare, but valid).

## Timing semantics

Scheduling is **fixed-delay**: the next invocation starts `1000 / hz` milliseconds after the previous one *finishes*.

- A slow loop never overlaps itself.
- The **effective rate is `hz` or lower** — a 20 ms body at `hz = 50` actually runs ~25 Hz.
- The first invocation happens immediately at registration.
- All non-hardware loops share the 8-thread scheduler pool, so a blocked loop can delay others scheduled at the same moment; hardware loops are isolated on the hardware thread.

```java
@RunPeriodically(hz = 20, hardware = true)
public void drive() {
    double y = -orchestrator.getLatestValue("g1/left_stick_y", Float.class)
                             .map(Float::doubleValue).orElse(0.0);
    left.run(m -> m.setPower(y));
}
```

## Gate labels

`labels` gives the loop's ticks [gate labels](/docs/ftc/hardware-actions), so one `hardware().restrict("write", ...)` can freeze a whole family of loops at once:

```java
@RunPeriodically(hz = 50, hardware = true, labels = "write")
public void drive() { /* every tick is labelled "write" */ }
```

- While a gate restriction covers any label, **that tick is skipped** — under `DROP` *and* `QUEUE` alike. Ticks are never held or queued: a tick is stale the moment it is late. The loop resumes on its normal schedule once the label is released.
- **Periodic work has no slots.** A tick is one tick — there is nothing to coalesce. (`Scope.bulkRead(...)` on a slotted scope throws `IllegalArgumentException` for the same reason.)
- `labels` without `hardware = true` logs a warning and does nothing — the gate governs the hardware thread.
- Malformed labels throw at `registerNode`; the reserved `HardwareGate.ALL` / `HardwareGate.UNLABELLED` roots cannot label a tick. The single-element shorthand `labels = "write"` works in Java.

## Error behavior

An exception in the body is logged and the loop keeps running — a single throw does not kill the schedule.

> **Choose `hardware = true` for anything that reads or writes devices.** A loop that forgets the flag runs on the scheduler pool, where every hardware call is a rule violation — and `SafeDevice` calls made from there enqueue onto the hardware thread with extra latency. The flag costs nothing and prevents both.
