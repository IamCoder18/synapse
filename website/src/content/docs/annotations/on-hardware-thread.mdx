# @OnHardwareThread

`@OnHardwareThread` marks a `@SubscribedTo` method as hardware-touching. The binder re-routes the handler to the orchestrator's single dedicated hardware thread, where it executes strictly serially with every other piece of hardware work.

```java
@SubscribedTo(topic = "intake/set/power")
@OnHardwareThread
public void onTarget(double power) {
    intake.run(m -> m.setPower(power));
}
```

## Attributes

| Attribute | Type | Default | Meaning |
| --- | --- | --- | --- |
| `labels` | `String[]` | `{}` | gate labels for every dispatched message |
| `slot` | `String` | `""` | coalescing slot for the dispatches |

Both are optional — with neither, the annotation is still a pure marker. It only affects methods that also carry `@SubscribedTo`.

## Labels and slots

`labels` gives each dispatched message [gate labels](/docs/ftc/hardware-actions) — `/`-separated paths like `"write"` or `"write/drive"`; the path structure is the hierarchy. While a gate restriction covers any of the labels, dispatches of this method are dropped or held per the restriction's `GateMode`. The single-element shorthand `labels = "write"` works in Java; use `labels = {"write", "climb"}` for several. Malformed labels throw at `registerNode` — a bad label fails before the first dispatch — and the reserved `HardwareGate.ALL` / `HardwareGate.UNLABELLED` roots cannot appear here.

`slot` claims a coalescing slot: **only the newest undelivered dispatch survives**. A newer message supersedes an older one that has not started (it fails with `Reason.SUPERSEDED` — see [what happens when work is blocked](/docs/ftc/hardware-actions#what-happens-when-work-is-blocked)), so a flooded topic collapses to its latest value instead of piling up. That makes slots ideal for setpoint topics: whatever gate state was, the hardware applies the driver's *current* command, not a replayed queue of stale ones. The slot is an opaque string — no hierarchy, no escapes; empty means no slot.

```java
@SubscribedTo(topic = "drive/set/power")
@OnHardwareThread(labels = "write", slot = "drive-power")
public void onPower(double p) {
    motor.raw().setPower(p);
}
```

Labelling is optional: with no labels, the gate can only reach this method through `HardwareGate.ALL` or `HardwareGate.UNLABELLED`. With a label, one `restrict("write", ...)` can hold or drop every write-side dispatch at once — see the [gating guide](/docs/guides/gating-hardware) for the patterns.

## Why a dedicated thread

FTC hardware is not thread-safe. The Lynx bus, `DcMotorEx`, servos, the IMU, and I²C sensors all misbehave when driven from two threads — race conditions, garbled serial responses, `ConcurrentModificationException` crashes deep in the SDK. The orchestrator owns exactly one thread for hardware, and `@OnHardwareThread` is how a callback opts into it.

The same thread serves:

- `@OnHardwareThread` subscribers,
- `@RunPeriodically(hardware = true)` loops,
- `HardwareActions.run/call/callAsync/bulkRead` submissions.

Work on it is strictly serial — no locks are needed anywhere in user code.

## What it does not do

- It does **not** intercept hardware calls made from unannotated code. A raw `motor.setPower(...)` inside a plain `@SubscribedTo` method still runs on the callback pool.
- It does **not** protect `onSafeLoop()`. `SafeOpMode.loop()` asserts *its own* thread; if your OpMode loop touches hardware directly, that touch happens off-thread. Move it into a node, or use `SafeDevice.run(...)` from the loop.
- It does **not** apply to `@RunnableAction` methods — actions always run on the action pool.

## The deadlock rule

> **Never block waiting for the hardware thread while on it.** Calling `hardware.call(...)` or `device.call(...)` inside an `@OnHardwareThread` subscriber, a `hardware = true` loop, or a bulk-read reader hangs the robot: the one thread is waiting for a task it cannot start. Code already on the hardware thread should use `device.raw()` and touch the device directly.
